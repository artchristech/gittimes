Free Open Textbook Walks Builders From Silicon Sand to Finished Chip 🔗

Beginner-friendly guide maps fab process flow, terminology and know-how without requiring semiconductor physics background

chenwei810/Semiconductor_Manufacturing_Introduction · Python · ▲ 193 in 1d 5d old

Software engineers, hardware-curious developers and manufacturing newcomers now have a plain-language map of how chips get made. chenwei810/Semiconductor_Manufacturing_Introduction is an open book that follows a single silicon wafer from raw sand through the fab, test and packaging, ending when it becomes a usable chip.

The approach is deliberately practical. Rather than derive device physics, the book focuses on the things a fab floor actually runs on:

  • Process flow: the sequence of steps a wafer passes through, and why order matters
  • Terminology: the vocabulary engineers use daily, defined in dedicated term boxes
  • Know-how: practitioner tips collected in know-how boxes in every chapter

Numbers are presented as orders of magnitude, since real values vary by process, product and company. The project states it draws only on public information and general industry knowledge, with no confidential parameters or internal procedures, and it is not affiliated with any semiconductor company.

Contribution is built in. Errors can be reported through an "Erratum" issue template, and the repository includes a contributing guide and style guide for new chapters and figures. The text and images are licensed CC BY-NC-SA 4.0, so educators and self-learners can share and adapt them for non-commercial use.

The project has drawn attention on GitHub, with 94 forks and one open issue at the time of writing. It is a young repository, created in October 2026, so its content is still settling.

The catch: The book trades depth for accessibility by design. Readers who need device physics, equipment specifics or exact process parameters will have to look elsewhere, and its figures are approximations rather than engineering references.

Why this leads today It leads because a Python-based introduction to semiconductor manufacturing gives the growing crowd of engineers and students entering chip and hardware work a practical reference for fab-related tooling and modeling, while the competing roast-room prompt tool would affect few builders' daily work.

Use Cases
  • Software engineers learning hardware fundamentals for chip-adjacent product work
  • Students preparing for semiconductor coursework needing a process-flow primer
  • Career changers evaluating entry into fab operations, test or packaging roles

Eleven Lets AI Agents Reverse-Engineer Binaries, Android Apps and GPU Kernels Side by Side 🔗

Open-source app hands any Agent Client Protocol agent a working window into native code, with every change logged and reversible

Zfinix/eleven · TypeScript · 563 stars 2d old

Eleven is a reverse-engineering app built around agents rather than around the analyst alone. Drop in a binary, an Android APK, a GPU kernel or a shader, then ask an agent what it does.

Agents read code, follow references, rename functions, leave notes and propose patches while you watch and approve in the same window.

The design is the point. Eleven serves its own MCP tools, so an agent can open a function, switch views, rename symbols and change types directly. Select lines in pseudocode, assembly or source and ask for an explanation; the answer appears beneath the lines, and suggested renames arrive as cards you accept or decline.

Native code is handled by Ghidra through REA, or by Rizin when files need to open in seconds. Android apps open with Java from jadx, smali from apktool when installed, and split bundles (.xapk, .apks) with every split in place. Mach-O, ELF and PE are supported.

Control stays with the human. Every change, from you or an agent, is logged with its author and can be undone. Byte patches from agents arrive as suggestions, never applied silently.

Bring your own agent: Claude, Codex, Gemini, Cursor, Copilot, OpenCode or any ACP-compatible agent. Several can run on one project in separate chats. The current release is v0.1.9, a TypeScript codebase built on React rendered through GPUI.

The catch: The project is very new, created in October 2026, with eight open issues and a 0.1.x version number. Its agent-driven write access to binaries is powerful, so builders should test patch workflows on disposable samples before trusting them on production artifacts.

Use Cases
  • Security researchers auditing binaries with AI agents alongside Ghidra analysis
  • Mobile engineers inspecting decompiled Android APKs and split bundles quickly
  • GPU and shader developers asking agents to explain unfamiliar compiled kernels

A community project called uncharted_pc runs the original PS4 code for Uncharted 1, 2 and 3 directly on Windows 10 and 11. Graphics are translated to Vulkan rather than emulated at the hardware level.

Owners supply their own decrypted game dump. No game files ship with the project, and it is not affiliated with Sony or Naughty Dog.

  • All three games launch from one executable
  • 60 or 120 FPS targets, with TAA, FSR 3.1/4 and DLSS options

Fan Port Runs Shadow of the Colossus Natively on Windows PCs 🔗

Project translates the PS4 game's GPU code to Vulkan, but requires users to supply their own game dump and console audio modules

AjncSystem/ShadowOfTheColossus-PC · C++ · 716 stars 3d old

A community project called ShadowOfTheColossus-PC is building a native Windows port of Bluepoint's 2018 PlayStation 4 title. The game's x86-64 code runs directly on the PC's CPU, while the PS4's graphics are translated to Vulkan.

The project is not an emulator. It is a loader that supplies the system functions the game needs, in the style of the bloodborne_pc port. It ships no Sony or game files.

  • Users must provide their own CUSA08809 dump.
  • Sound requires two modules, libSceNgs2.sprx and libSceUlt.sprx, taken from an existing shadPS4 install.
  • The launcher auto-detects these on the PC's drives.
  • Requirements: Windows 10/11 64-bit and a GPU with Vulkan 1.3.

Version 0.57 fixes green and pink color corruption on AMD cards. That fix has not yet been tested on AMD hardware. The first launch after updating recompiles shaders and stutters.

The catch: The project has 74 open issues, and AMD fixes remain unverified on AMD hardware.

Use Cases

  • Preservationists documenting PS4-to-Vulkan translation of console-era games.

Open-Source Server Lets Coding Agents Land Code Without Merge Queues 🔗

MIT-licensed fork of Gitaly adds server-side history, compare-and-swap landings and any-provider conflict resolution.

feder-cr/open_scion · Go · 1k stars 0d old

Anthropic's internal Scion system redesigned source control for hundreds of agents writing code at once. Now open_scion offers an independent, MIT-licensed implementation of that design that anyone can run.

Classic Git hosting assumes humans who clone, work for hours and push once. Agents make thousands of short tasks that each want to land in seconds. open_scion moves the work to the server:

  • Clients fetch only the objects they need.
  • History queries are computed and cached server-side.
  • Changes land via compare-and-swap rather than a merge queue.
  • Every reference update is recorded in a changeset log.

It is a fork of GitLab's Gitaly, and repositories remain standard Git. The server never calls a language model, so conflict resolution works with any provider or none.

The catch: the project is at v0.1.0 with one open issue, and its scale claims rest on an architecture that has not yet been proven under production agent load.

Use Cases
  • Platform teams running fleets of coding agents against shared repositories.
  • Self-hosters wanting agent-scale Git without a single-vendor dependency.
  • Researchers testing server-side version control designs for autonomous code changes.
