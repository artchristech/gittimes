Local Mac Server Lets Developers Run Open Models Without Python or Cloud 🔗

One Zig-built server speaks OpenAI, Anthropic and Ollama APIs, adding image, video, music and speech generation on Apple Silicon.

ddalcu/mlx-serve · Zig · ▲ 18 in 1d 8mo old · Latest: v26.10.2

mlx-serve lets developers run open-weight models entirely on an Apple Silicon Mac, with no Python runtime, no account and no network dependency. The server listens on localhost:11234 and answers requests written for the OpenAI, Anthropic and Ollama APIs, so existing clients can be pointed at it without code changes.

The backend is written in Zig, with a Swift macOS app layered on top for chat and generation. The project's own release notes highlight the scope beyond text:

  • Coding agents: mlx-serve launch claude starts Claude Code against a local model, configured to the model's real context window.
  • Media generation: image, video, music and speech models, including FLUX.2 and Qwen3-TTS with voice cloning, run in the app or over HTTP.
  • Large models: the README says some mixture-of-experts models larger than system memory can run on a 128 GB Mac by streaming experts from SSD, and two Macs linked by Thunderbolt 5 can share one model.

For builders, the appeal is a single local endpoint that replaces a cloud API for development, private transcription and offline assistants, under an MIT license. The project also ships Linux builds for NVIDIA GPUs and an iPhone build.

The catch: The project is roughly eight months old and carries 67 open issues, and its quality on media-generation models is not independently benchmarked here. It requires macOS 26.2 on Apple Silicon, so it is no help to Intel or Windows developers, and anyone adopting it for production should verify how the SSD-streaming path performs on their own hardware before relying on it.

Why this leads today It offers developers a new way to run local models on their own Macs, plugging into existing OpenAI and Anthropic tooling without Python, while today's other contenders are niche or long established.

Use Cases
  • Mac developers running Claude Code or Codex against a local model offline.
  • Teams keeping transcription and meeting notes on-device for privacy reasons.
  • App builders swapping a cloud LLM endpoint for a local OpenAI-compatible server.

Source: ddalcu/mlx-serve — based on the README and release notes.

Reason Network Lets Teammates' Coding Agents Message Each Other Directly 🔗

One Rust daemon per machine, no server, and it works across ten agent tools including Claude Code and Cursor.

reason-machines/reason-network · Rust · 527 stars 3d old

A new open-source project lets coding agents on different developers' machines find each other and exchange messages without a central server. The engine behind reason network runs as one small daemon per computer and connects peers directly.

Every active agent session on a teammate's machine appears in a shared roster. Each entry shows who is running it, which repo and branch it is on, whether it is busy or idle, and what it is doing now. Any agent can message the right peer, or send up to 10 text files of 256 KB each, 512 KB total.

Agents get three tools: list_team, send_message and ask_user, plus check_inbox where push delivery is unavailable. Delivery depends on the host. Claude Code, Codex, opencode, pi and Reason receive messages mid-session and wake idle sessions. Cursor, Gemini, Copilot and Grok receive them at their next step. Hosted assistants connect through an MCP endpoint.

Version 0.11.1 is a small patch. It changes how a removed machine handles a replacement invite link, and moves joining to Reason browser sign-in.

The catch: The project is young. It has a single tagged release line, two open issues, and an install path that depends on Reason's hosted sign-in and an invite-link flow. Builders should test peer discovery and message delivery on their own network before relying on it for team workflows.

Use Cases
  • Engineering teams sharing live coding-agent status across developer laptops
  • Developers having one agent request help or files from a teammate's agent
  • Multi-tool teams coordinating Claude Code, Cursor and Codex sessions together

Source: reason-machines/reason-network — based on the README and release notes.

Claude Code Strips Ads From Old Android TVs in Minutes 🔗

A prompt-driven cleanup disables bloatware and sponsored rows, leaving apps, HDMI inputs and a clock.

Ansub/tv-detox · Java · 758 stars 2d old

A new GitHub project lets an AI coding agent do the tedious work of rescuing sluggish Android TVs. Users paste a prompt into Claude Code or Codex on a laptop on the same Wi-Fi network, then press OK on the remote.

The agent turns off bundled apps and sponsored home-screen rows through adb, leaving a minimal screen with your apps, HDMI inputs and a clock. Nothing is deleted. Every change can be reversed, and the agent asks before each one.

Google TV and Chromecast users need care. Version 1.4.1 keeps the device's own home screen running by default, after some units got stuck restarting and needed a factory reset. Newer models require Wireless debugging with a pairing code.

The catch: the project has 13 open issues and is a single-maintainer tool with no guarantee of support, so back up your settings before you run it.

Use Cases
  • Households with aging Android TVs wanting ad-free home screens without technical work.
  • Hotel or office staff tidying shared TVs of identical models.
  • Developers adapting the prompt to clean up other low-power Android devices.

Open-Source Rust CAD Lets Builders Rebuild Models From a Single Dimension 🔗

SolidCraft runs on desktop and in the browser, and AI agents can model through its built-in MCP server.

tangency-labs/solidcraft · Rust · 7.9k stars 1w old

SolidCraft is an open-source parametric 3D CAD application written entirely in Rust. Users sketch, constrain and extrude solids along a feature timeline, then change one dimension and watch the model rebuild.

The project ships as a desktop app for Windows, macOS and Linux, and as a web app that needs no install. A built-in MCP server lets AI agents drive modeling directly.

The project's own demo builds a Raspberry Pi 4 case from an empty document, with mounting standoffs, vents, engraved text and a material definition, then changes the height and regenerates the part.

The team reports that 75 of 76 public reference parts match analytic or FreeCAD-computed volume, area, centre of mass and bounding box. The latest release, v0.16.2, is a navigation fix.

The catch: the project is early, with 1,565 open issues, and its downloads are not yet code-signed, so builders must bypass SmartScreen or Gatekeeper warnings on first run.

Use Cases
  • Hobbyists designing enclosures and brackets for 3D-printed electronics projects
  • Engineers prototyping simple parametric parts in a browser without installing software
  • Developers automating CAD workflows where AI agents generate and revise models

Orca Lets Builders Run Five Coding Agents Side by Side 🔗

Each agent gets its own git worktree, and results can be compared or merged from desktop or phone.

stablyai/orca · TypeScript · 99.1k stars 7mo old

Orca is an orchestrator for coding agents. Developers can run Codex, Claude Code, OpenCode or Pi in parallel, each in an isolated git worktree, then compare outputs and merge the winner.

The latest release, v1.4.232, shifts focus to permissions and remote work:

  • Auto permissions: Settings now offer Manual, Auto and Yolo modes. Auto lets supported Claude and Codex agents handle their own approvals.
  • Phone control: Orca Monitor sends notifications when an agent finishes and accepts follow-up prompts from anywhere.
  • SSH recovery: Managed servers reconnect after lost pairing, and tunnels follow a restarted server's port.

Orca also tracks Claude and Codex usage and rate-limit resets, and it can hot-swap accounts.

The catch: The project shows 8,576 open issues, and the Auto permission mode hands approvals to agents, so teams should test it on non-critical repositories first.

Use Cases
  • Solo developers comparing outputs from several coding agents on one task.
  • Engineers steering long-running agent jobs on remote servers from their phones.
  • Teams reviewing agent-generated diffs and sending line comments back before committing.

Source: stablyai/orca — based on the README and release notes.

Open-Source Script Strips Ads and Tracking From Fire TV Sticks 🔗

Tool works over ADB without root, touches nothing in system partitions, and reverses in one script.

humblemuzzu/dumbtv · JavaScript · 785 stars 1d old

A GitHub project called dumbtv applies a simple rule to Fire TV sets: keep the apps you chose and the HDMI inputs you use, and drop the rest. It runs from another machine over adb, needs no root, and writes nothing to /system.

The project ships a replacement home screen, dumbtv-home.apk, at 45 KB with no internet permission and no advertising ID. Fire OS 7 and 8 need no permissions at all. A separate catalog tracks which models work and which dialogs block automation.

Tested so far on Fire OS 7.7.1.7 (Android 9) and Fire OS 6 for older sticks. Android TV needs a different package list and launcher approach. The tool does not replace the operating system, unlock a bootloader, or survive a factory reset.

The catch: the repo has 28 open issues and per-model coverage depends on volunteers filing device reports, so untested sets may not work.

Use Cases
  • Households wanting Fire TV without built-in ads or viewing tracking
  • Tinkerers scripting reversible ADB changes across multiple Fire TV devices
  • Contributors documenting per-model Fire TV quirks for a shared device catalog

Source: humblemuzzu/dumbtv — based on the README and release notes.

OpenList Forks AList to Keep Cloud Storage Governance Community-Owned 🔗

Latest release adds 500 GB uploads on China Mobile's 139 cloud and md5-based instant uploads on Guangya Pan

OpenListTeam/OpenList · Go · 25.1k stars Est. 2025

OpenList is a Go fork of the AList file-listing server, built by an independent team to keep governance in community hands rather than a single maintainer. It unifies access to multiple cloud drives, including Aliyundrive, OneDrive and local storage, behind one interface.

The newest release, v4.2.7, focuses on driver work:

  • drivers/139 now uploads files up to 500 GB and lets users choose the API client type.
  • drivers/guangyapan adds md5-based instant upload.
  • drivers/pikpak re-logs in automatically when tokens expire.
  • server/s3 gains multipart upload.

The project's license is AGPL-3.0, and it has explicitly disavowed look-alike commercial forks that use its name.

The catch: the project has 302 open issues, and driver support depends on third-party cloud APIs that can change without notice.

Use Cases

  • Teams needing large-file transfers to Chinese cloud storage through a single open-source gateway

A new cluster of open-source projects suggests the center of gravity is moving away from models and toward the harness: the software that schedules, observes, and corrects agents doing real work.

Several repos are building the review loop.

plannotator lets developers annotate agent plans and diffs visually and send feedback back to the agent in one click. scrawl lets you mark up a screenshot, record a problem, and hand it to an agent. Both treat human correction as a first-class interface rather than an afterthought.

Others focus on multi-agent orchestration. agent-of-empires manages several Claude Code and OpenCode sessions from a TUI or web UI, while orca and nexting add mobile and remote control. pipeshub-ai goes further, exposing company knowledge through permission-aware search that agents can grep and cite via MCP.

A quieter branch targets hardware. tv-detox and free-my-tv use coding agents to rebuild ad-free Android TV home screens, and mlx-serve runs OpenAI- and Anthropic-compatible inference natively on Apple Silicon.

What ties these together is that the artifacts are increasingly generated by agents and then governed by humans through lightweight tooling.

The catch: Most of these projects are weeks old, lean on proprietary APIs and subscriptions, and lack shared standards for permissions, state, or evaluation. "Harness" is still a loose term, and the review-and-correct loop has not been shown to scale beyond solo developers.

A pattern is emerging across this cluster: specialized, domain-heavy tools are being rebuilt on modern web-frameworks rather than native toolkits. The shift is less about aesthetics than about shipping one codebase to desktop, browser, and automation surfaces at once.

Consider what these projects just delivered:

  • Blink pairs Tauri with React to deliver a desktop Jellyfin client, wrapping a web UI in a native shell.
  • URDF-Studio runs a 3D robot modeler in the browser, with MuJoCo export and AI assistance layered onto the workspace.
  • SolidCraft takes the opposite route: a parametric CAD engine written in pure Rust, exposed through desktop, web, and MCP automation.
  • open-claude-ui reverse-engineers the Claude desktop interface into 30 React components with a detailed interaction analysis.
  • agent-of-empires manages multiple coding agents from either a terminal UI or a web view, explicitly targeting phone access.

The common thread is the interface layer. Engines are increasingly written in systems languages, while the surface is a web or web-derived component tree. Protocols like MCP and OpenAI-compatible APIs let the same backend serve humans and agents. The web stack has become the universal presentation layer for tools that were once native-only.

The catch: This is early and uneven. Wrapping web UIs in desktop shells often trades performance and native integration for velocity, and several repos here are young, single-maintainer efforts. Calling it a settled framework trend overstates what a small sample shows.

  • Robotics engineers previewing and exporting URDF robot models in a browser.

pytorch/pytorch · Python · ▲ 31 in 1d Est. 2016 · Latest: v2.14.1

PyTorch v2.14.

1 is a correctness release. Most of its fixes target results that were wrong without raising an error, the category most likely to slip into a training run or a numerical pipeline unnoticed.

On Apple Silicon, torch.linalg.lstsq could return incorrect solutions for complex batched underdetermined systems. torch.linalg.svd could produce a non-orthogonal U and inaccurate small singular values on rank-deficient or ill-conditioned inputs. For teams running mixed Apple and NVIDIA hardware, the practical step is to pin to 2.14.1 and rerun any linear-algebra-heavy evaluation that previously passed.

The catch: The release fixes bugs but does not explain how many users hit them or whether earlier results need recomputing. Teams should check whether their outputs depended on the affected code paths before assuming prior runs were sound.

OpenIPC/firmware · C · ▲ 4 in 1d Est. 2021 · Latest: nightly

OpenIPC's firmware now targets far more than its original HiSilicon base. The project's README lists support for chips from Ambarella, Anyka, Fullhan, Goke, GrainMedia, Ingenic, MStar, Novatek, SigmaStar and XiongMai, with more expected.

For owners of cheap IP cameras locked into vendor firmware, that breadth matters: one open image can replace proprietary software across multiple hardware families.

The project is written in C and built on Buildroot and U-Boot. Its latest nightly build, from commit 5e914f7 and built October 19, ships with a checksummed web UI. Development is split across two tiers: free community support via chat, and paid commercial support from core developers, with revenue flowing through Open Collective.

Contributors are pointed to CLAUDE.md and AGENTS.md before submitting patches, a sign the tree has grown complex enough to need formal contributor guidance.

The catch: The project has 171 open issues, and it ships only nightly builds rather than tagged stable releases. Support breadth is also uneven: a chip appearing in the README does not guarantee every camera model on that SoC works. Businesses should verify their specific hardware before committing to a deployment.

Nexting connects a phone or wearable to agents already running on a Mac or Windows PC. Users can view live sessions, send tasks, and steer Claude Code, Codex, Grok, and Cursor remotely.

The hardware is the new part. The PIN, a collar-mounted device priced at $129, is shipping now. A ring-form Ring remains in private beta. Both pair over Bluetooth and dispatch a spoken task in about three seconds.

The build centers on:

  • Fifteen Feetech 1910 serial servos
  • An Arduino UNO Q controller
  • A custom expansion board with an IMU and servo interfaces
  • A movable head and beak, driven by a separate mouth servo

Companion repositories supply the onboard runtime and reinforcement-learning tools, so builders can move from assembly to motion experiments. The motion policy targets 14 joints.

The project has drawn 90 forks and five open issues. A recent hardware correction reverses GND and SIGNAL on three components of the older board, so owners of early boards must rewire before powering up.

The catch: the maintainers warn the hardware is for learning and testing only, and that mass-production PCB fabrication is not recommended.

PlayCanvas Engine Pushes Gaussian Splatting Into Mainstream Browser Workflows 🔗

Latest release fixes render-container warnings as the open-source runtime keeps expanding WebGPU and splat support for browser-based 3D.

playcanvas/engine · JavaScript · ▲ 3 in 1d Est. 2014 · Latest: v2.23.3

The playcanvas/engine runtime is an open-source 3D engine written in JavaScript that targets WebGL2 and WebGPU directly in the browser. Its newest tagged release, v2.

23.3, is a narrow fix, but the surrounding feature set shows where the project is heading.

The engine's most distinctive recent emphasis is first-class support for 3D Gaussian Splatting. Splats are loaded and rendered as native scene content rather than through a bolt-on plugin, which matters for builders producing photogrammetry-style captures and volumetric environments for the web.

For developers, the practical surface includes:

  • Physics through the ammo.js rigid-body integration
  • XR via WebXR for AR and VR sessions
  • Assets streamed asynchronously over glTF 2.0, with Draco and Basis compression
  • Scripting in TypeScript or JavaScript

Release v2.23.3 changes one behavior: render containers that were never registered now trigger warnings only when preload begins, cutting noise for projects that register containers late. The release is a patch, not a platform shift.

The catch: The repository carries 463 open issues, and the engine's breadth means many of its subsystems move at different speeds. Teams betting on the newest rendering path, particularly WebGPU and splatting, should test on their target devices before committing.

flame-engine/flame · Dart · 10.8k stars Est. 2017

Flame, the Dart game engine built on Flutter, has spent nearly nine years giving Flutter developers the plumbing games need: a game loop, a component system, collision detection, and input handling. What's new is the 3D path.

The flame_3d_component bridge adds 3D components to Flame's component tree, built on flutter_scene.

The most recent release, flame_3d-v0.3.2, is narrow. It republished the package with a Flutter 3.47.0 constraint so it installs cleanly on current toolchains. For builders, the point is that the 3D bridge is now usable against the Flutter version most teams are on.

Flame also ships official bridges for flame_audio, flame_behavior_tree and others, so a project can extend the engine without leaving the Flame component model.

The catch: the 3D bridge is at version 0.3, and the repository carries 82 open issues, so teams should check that the features they need are stable before committing a production title.
