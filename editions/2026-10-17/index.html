Indra OCR Reads Pages at 49 Per Second on Ordinary CPUs 🔗

A 1M-parameter model with an 18 MB footprint turns PDFs and scans into structured markdown without a GPU or PyTorch.

datalab-to/indra · Python · 555 stars 4d old · Latest: v0.3.1

Most document pipelines still send pages to GPUs or heavy frameworks just to extract text. Indra OCR takes a different path.

It is a compact OCR system built for speed on commodity CPUs, and it converts PDFs and images into markdown, plain text, or JSON.

The numbers are the reason builders are paying attention. According to the project's README, Indra reads up to 49 pages per second on CPU, roughly 11 to 17 times faster than Tesseract and PaddleOCR on the same pages. On four x86 vCPUs, latency sits near 230 ms per page.

Several design choices stand out:

  • Layout-aware output. Every line and layout block gets a bounding box, labeled as headings, lists, tables, captions, footnotes, or page headers, with reading order preserved.
  • Born-digital PDFs are handled first. Indra reads the embedded text layer in any script and runs OCR only on what is missing.
  • Small footprint. The models total about 18 MB on ONNX Runtime, with no PyTorch dependency. The core recognizer, rec.onnx, has roughly 1M parameters.

Installation is a single pip install indra-ocr, and the models download from Hugging Face on first run. The project is Apache-licensed and ships a viewer, indra-ocr-viewer, for inspecting line and block output.

Accuracy is competitive on the project's own benchmark, scoring 41.3 on OmniParseBench text against PaddleOCR's 35.8 and Tesseract's 19.3. Those are self-reported results, and independent replication would strengthen them.

The catch: Indra is young. Version 0.3.1 is its first public line, the repository has two open issues, and the README's own limitations section concedes weak spots in complex tables, handwriting, and scripts outside its supported list. Teams with those workloads should benchmark before adopting it.

Why this leads today Document parsing sits inside many RAG, ingestion and automation pipelines, and OCR that produces ordered markdown without a GPU or cloud service is something many builders will need to evaluate.

Use Cases
  • Data teams batch-converting large PDF archives to markdown on CPU servers.
  • Developers adding fast document ingestion to RAG pipelines without GPU budgets.
  • Edge and serverless builders needing OCR within a small, PyTorch-free footprint.

Overdrive Revives PS5 Homebrew Game Store After Original Project Shut Down 🔗

Rebuilt from a decompiled binary, the C++ client now lists over 1,800 games and installs itself from the console.

MyLuxy/overdrive · C++ · 598 stars 3d old

The original Overdrive, a PS5 homebrew game store, has been shut down. A developer decompiled its last released build, recovered the source and rebuilt it, publishing every line under the MyLuxy/overdrive repository.

The v1.0.5 release fixes download hosts and adds new features.

The app browses more than 1,800 games with filters, sorting, scores and download sizes. It downloads directly to the console's internal storage or any USB drive, showing live speed and storage stats. Favorites, an on-screen keyboard search and a Files page for cleaning up drives round out the interface. It ships in 13 languages and is driven entirely by the controller.

Installation runs on a jailbroken PS5 with two payloads: ShadowMount+, which mounts .exfat images automatically, and kstuff. The user copies Overdrive.exfat, unmodified, into a lowercase homebrew folder on an exFAT USB drive. ShadowMount+ detects the file and installs it without further input. The app updates itself from the console.

Recent fixes address DataNodes, FileKeeper and LinkVault downloads, games extracted to the wrong folder, and focus handling in grids. New additions include a rotating home page, Dutch language support and vibration intensity levels.

The catch: The project is a reconstruction from compiled code, not an original codebase, and it carries 13 open issues. It depends on a jailbreak and two third-party payloads, and the library's download sources have shifted repeatedly, so availability will remain fragile.

Tencent-Hunyuan/Hy-Memory · Python · 541 stars 2d old

Tencent's Hunyuan team has open-sourced Hy Memory, a Python engine and SDK (hy-memory) that gives LLM agents structured long-term memory instead of a flat context window.

The system splits memory across three task scenes:

  • Chat: an eight-layer hierarchy running from raw dialogue to atomic facts, summaries and schemas.

Earshot Gives Coding Agents Ears to Hear the Sound They Make 🔗

Open-source CPU-only tool lets agents synthesize sounds in code, then judge and revise them by listening.

Leonxlnx/earshot · Python · 626 stars 2d old

AI coding agents can now write code that renders a film or a game, but they cannot hear what they produced. earshot closes that gap.

It turns audio into evidence an agent can reason about: a plain-language description of a file, a score for how well it matches a prompt, and a second-by-second transcript of a full film.

The project also lets agents make sound. Its forge component builds sounds from physical synthesis recipes, with resonators, filtered noise and computed rooms, and a critic scores each candidate by listening. Its fit command reads a recording and writes readable Python that replays it from numbers alone. On 12 real recordings, the code renders reached a median 0.945 CLAP similarity to the originals.

It runs locally on CPU as a CLI, a Python API and an MCP server:

  • Listen: describe, score and transcribe audio
  • Forge: generate and iteratively refine sound effects in code
  • Fit: convert recordings into editable synthesis recipes

The catch: the project is young at v0.2.0, each CLI call reloads models for 20 to 40 seconds, and its similarity claims rest on the authors' own blind tests.

Use Cases
  • Video agent builders generating motion-design sound effects without recorded assets.
  • Game developers prototyping parameterized impact and UI sounds as editable code.
  • Audio engineers converting reference recordings into tweakable synthesis recipes.

gitai Brings Agent-Scale Version Control to Any Git Host 🔗

Open-source server moves history work off clients and lands changes via compare-and-swap, skipping merge queues.

feder-cr/git-ai · Go · 1.1k stars 2d old

A new MIT-licensed server, gitai, aims to make Git work for swarms of coding agents. It is an independent implementation of a design Anthropic described in its engineering writing, and it is not affiliated with Anthropic.

Classic Git hosting assumes humans who clone, work for hours and push once. Agents make thousands of short tasks that touch a few files each and want to land in seconds. The project's answer moves the work to the server:

  • Clients stay online and fetch only what they need.
  • History queries are computed and cached server-side.
  • Changes land through a compare-and-swap rather than a merge queue.
  • Every accepted update is recorded in a changeset log.

Repositories remain normal Git underneath. The server never calls a language model; AI features plug in through any provider or none. Version 0.1.0 is the first release, built on Gitaly, and it requires Go 1.26 and a C toolchain.

The catch: v0.1.0 is a first release with zero open issues and no track record yet, so its behavior at agent scale is unproven.

Use Cases
  • Platform teams running hundreds of concurrent coding agents on shared branches.
  • Self-hosters wanting agent-friendly Git without depending on a single vendor.
  • Researchers testing automated conflict resolution and post-merge verification at scale.

Source: feder-cr/git-ai — based on the README and release notes.
