Git Core Team Refines Patch Workflow to Streamline Kernel-Style Contributions 🔗

Recent updates to GitGitGadget lower barriers for developers submitting C-based improvements via mailing list

git/git · C · ▲ 23 in 1d Est. 2008

Git remains the foundational distributed version control system powering millions of software projects, with its core implemented in C for performance and low-level control. Its development model relies on a public-inbox mailing list workflow rather than GitHub-native pull requests, requiring contributors to format patches according to Documentation/SubmittingPatches.

The GitGitGadget tool bridges this gap by converting GitHub pull requests into properly formatted patches for submission to git@vger.kernel.org, reducing friction for newcomers. Recent activity shows maintainers actively refining this pipeline, with the last commit just one day ago and ongoing work to improve patch automation and documentation clarity. This focus on contribution ergonomics comes as the project sustains high engagement—28,513 forks and 402 open issues indicate vigorous community involvement despite its mature codebase. Git’s design prioritizes speed, integrity, and support for non-linear workflows, making it indispensable for kernel-scale collaboration. Its command set offers both porcelain convenience and plumbing access, enabling everything from simple commits to complex history rewrites. The project’s longevity stems from this balance of accessibility and depth, though its mailing list-centric culture remains a hurdle for developers accustomed to modern GUI-driven platforms.
The catch: Contributing requires learning Git’s patch submission etiquette, which can feel opaque compared to streamlined pull request flows on platforms like GitHub or GitLab.

Why this leads today Git's ongoing infrastructure improvements directly shape how developers collaborate and build software, making even incremental changes to its source code consequential for the entire ecosystem.

Rust-Based NVIDIA Driver Enables Metal on Intel Macs Running macOS Sequoia 🔗

Latest release fixes firmware write risks on AM5 systems while expanding GPU support

nullmoth/nvidia-macos-driver · Rust · ▲ 258 in 1d 5d old

NullMoth’s nvidia-macos-driver brings Metal support to NVIDIA RTX 20/30/40/50 series cards on Intel Macs using OpenCore, running macOS 15 Sequoia. Built in Rust, it wraps NVIDIA’s open GPU kernel modules (r610) to expose display and accelerator interfaces via NVRMFB and NVAccel, letting WindowServer composite through the NVIDIA GPU.

The driver does not require signed kexts; instead, it leverages user-approved extensions in Privacy & Security after first launch.

Release 1.14.3 addresses a critical firmware safety issue: macOS could write to AM5 motherboard firmware on Ryzen 7000/8000/9000 systems, potentially bricking the board. The fix leverages OpenCore’s DisableVariableWrite when OpenRuntime.efi loads, preventing unauthorized writes across reboots. This follows v1.14.0’s initial mitigation and now applies retroactively to older EFIs.

Installation requires downloading the nullmoth-nvidia-.tar.gz and 1401-Mac-.dmg from Releases, then running the 1401 installer after enabling extensions. Supported cards include GTX 16, RTX 20/30/40/50, TITAN RTX, and Quadro/RTX workstation GPUs, though device-table coverage exceeds physical validation—users must consult compatibility docs. The kernel-side design avoids reverse-engineering by using NVIDIA’s own open modules, reducing legal and stability risks.

The catch: Full-screen flicker persists on some machines, HDMI/DisplayPort audio remains unimplemented when hot-plugging monitors, and the “start once without driver” option can leave screens frozen—indicating ongoing stability gaps despite rapid iteration.

The catch: While promising, this contract-first approach risks fragmentation if competing standards emerge, and many tools still lack mature error handling, governance integration, or real-time enforcement—making them suitable for batch or development use today, but unproven in high-stakes, low-latency production environments where data contracts must be enforced with millisecond precision.

hajimehoshi/ebiten · Go · ▲ 1 in 1d Est. 2013 · Latest: v2.10.5

The latest Ebitengine release v2.10.

5 introduces audio playback support for WebAssembly builds, eliminating the need for Cgo when running Go 2D games in browsers. Previously, audio features like MP3, Ogg/Vorbis, and WAV decoding required Cgo, blocking pure Go compilation to WASM. This update integrates audio decoding directly into the engine using Go-native libraries, aligning with Ebitengine’s goal of simple cross-platform deployment. The release also includes minor bug fixes in input handling and texture atlas generation, per the project’s release notes. Ebitengine maintains its immediate-mode API, where game logic draws directly each frame without scene graphs, keeping boilerplate low for prototyping and small titles. Over 799 forks and active use in indie and educational projects show sustained adoption, though the engine intentionally avoids 3D, physics, or networking features to preserve simplicity.
The catch: Audio in WASM increases build size and may impact frame rates on low-end devices due to software decoding, offering no hardware acceleration alternative.
