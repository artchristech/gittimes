Terminal Multiplexer tmux 3.7c Fixes Critical Session Persistence Bug 🔗

Patch resolves utempter library integration failure affecting remote login tracking on Linux

tmux/tmux · C · 49.5k stars Est. 2015 · Latest: 3.7c

tmux remains the go-to tool for developers managing multiple terminal sessions within a single window, enabling detachment and reattachment without losing state. The 3.

7c release addresses a regression where utempter support—critical for updating utmp/wtmp login records—failed silently when the library was present but misconfigured, breaking audit trails on multi-user systems. This fix ensures proper session logging upon attachment, a necessity in enterprise and shared environments. Built in C with minimal dependencies (libevent, ncurses), tmux delivers low-latency multiplexing across BSD, Linux, and macOS, appealing to sysadmins and power users who prioritize reliability over flashy features. Its client-server architecture isolates session state, allowing background processes to survive SSH disconnects or local terminal crashes. Configuration remains text-driven, with key bindings and pane layouts defined via ~/.tmux.conf, scriptable but lacking a GUI—intentional for remote usability. Despite its age, the project shows steady maintenance, with the last commit just days ago and ongoing issue triage.
The catch: tmux’s steep learning curve and reliance on precise terminal compatibility (e.g., TERM variables, UTF-8 handling) can frustrate newcomers, and its lack of built-in session encryption means sensitive workflows still require external tools like SSH port forwarding or mosh for untrusted networks.

Why this leads today Tmux remains a critical tool for developer workflows, and its ongoing development reflects broader trends in terminal-based productivity that impact daily engineering practices.

Use Cases
  • Sysadmins monitor logs while editing configs in split panes
  • Developers run tests, servers, and editors concurrently remotely
  • Traders maintain market data feeds alongside analysis tools during volatility spikes

AnyJev Turns LLMs Into Typed Decision Models Without Retraining 🔗

Uses pooled hidden states and lightweight heads for calibrated probabilities in one command

nokia-applied-research/AnyJev · Python · 577 stars 4d old

AnyJev converts any LLM into a Jev-style decision model that outputs typed choices, scores, or yes/no answers with real probabilities—no fine-tuning needed. By pooling hidden states and attaching a small head, it serves calibrated decisions via `python -m anyjev.

pipeline`. The system works with transformers or vLLM backends, supports FP8 quantization, and measures accuracy, ECE, and latency on held-out data. It enables thresholdable decisions from a single model forward pass, avoiding logit parsing or engine patches.
The catch: Early-stage (v0.0.2) with open issues and limited validation beyond BANKING77 and Noul tasks.

A clear pattern is emerging in open source LLM tooling: the shift from conversational interfaces to action-oriented agents that perceive, decide, and act within existing digital environments. Rather than standalone chatbots, new projects integrate LLMs as invisible assistants that augment human workflows.

For example, jev-chat/jev-chat-jarvis reads on-screen messages in QQ, X, or Feishu via non-intrusive OCR, suggests replies, and one-click inserts them—leaving send decisions to the user. These projects share a technical ethos: minimal invasiveness, local-first processing, and composability—prioritizing user control over automation. The catch: While promising, this cluster remains fragmented across platforms and interaction models, with many tools relying on brittle screen-scraping or OCR that breaks with UI updates, and few demonstrating reliable, long-term autonomy in complex, real-world tasks beyond demos.

A clear pattern is emerging in open source: developers are rejecting fragmented, cloud-tied stacks in favor of self-contained, modular tools that bundle hosting, databases, AI runtimes, and DevOps into single, dependency-light packages. This shift prioritizes autonomy, low latency, and local-first execution.

For example, mikehasa/golive-skill lets users deploy agent-built products—complete with hosting, payments, and email—using only their own accounts via a zero-dependency Node CLI that follows a detect→plan→approve→apply→verify flow. Similarly, ddalcu/mlx-serve delivers native LLM inference on Apple Silicon via Zig, offering OpenAI-compatible APIs without Python or cloud calls, while mizorewww/laya-mlx achieves sub-15ms decision latency on M3 Max using MLX for typed models. On the frontend, heysagnik/diy-analytics enables instant analytics server setup in TypeScript, and expo/expo continues to unify React-native development across mobile and web. Even agent frameworks like bytechefhq/bytechef (Java) provide self-hostable AI workflow automation as an Apache 2.0 alternative to n8n. These projects share a core ethos: reduce reliance on external services by shipping capable, integrated runtimes that run locally or on user-owned infrastructure.
The catch: While promising for privacy and performance, this trend risks fragmentation—many tools reinvent wheels like auth or payment handling without shared standards, and tight hardware coupling (e.g., Apple Silicon via MLX) limits portability, leaving long-term interoperability and ecosystem cohesion unproven.
