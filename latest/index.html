Mistral's Timestral Forecasts Time Series on a Laptop CPU 🔗

Four model sizes from 5M to 209M parameters claim top benchmark rankings, with probabilistic forecasts over multivariate data and covariates.

mistralai/timestral · Python · ▲ 70 in 1d 6d old

Timestral is Mistral AI's family of time-series foundation models, built for multivariate probabilistic forecasting. Its standalone inference repository lets developers run predictions without training anything, using only PyTorch, NumPy, safetensors and huggingface_hub.

The approach is what makes it worth a closer look. Rather than fitting a separate model per dataset, a single pretrained model forecasts zero-shot, the way language models answer prompts without task-specific training. Key capabilities include:

  • Joint forecasting: the variates of a series are predicted together, not one at a time.
  • Covariates: past-only, known-future and categorical inputs are all supported.
  • Probabilistic output: 21 quantiles per time step, so teams get uncertainty ranges, not just point estimates.
  • Long context: up to 32,768 steps of history.
  • CPU-friendly inference: no GPU is required, lowering the barrier for small teams.

Long horizons are handled block by block, with each block's median fed back as context. Missing values are marked as NaN or through an observation mask.

According to the launch materials, the 209M-parameter model ranked first among pretrained and zero-shot models on GIFT-Eval, TIME and fev-bench. The four sizes also sit on the accuracy-versus-size Pareto front, which means no smaller model in the family is beaten on accuracy at its footprint. Those benchmark claims come from the vendor and have not been independently reproduced here.

The code is Apache 2.0, while the weights are released separately under a Modified MIT license, so read both before commercial use.

The catch: The repository is brand new, with five open issues and no tagged release, and the benchmark rankings are self-reported at launch. Teams should validate accuracy on their own data and check how the weights' license applies to their use case before building on it.

Use Cases
  • Demand planners forecasting inventory across many product lines at once
  • Energy analysts producing probabilistic load forecasts without GPU infrastructure
  • Data engineers adding zero-shot forecasting to existing monitoring pipelines

EAGLE-4 Sizes Speculative Decoding to Each Workload, Keeping Output Exact 🔗

The drafter tunes its speculation tree to the batch size, hardware and workload, and serves Qwen3.8-27B on SGLang, vLLM and TokenSpeed.

eagle-hq/EAGLE-4 · Python · 600 stars 0d old

EAGLE-4 is a new inference drafter for accelerating large language models. Its distinguishing feature is that it does not use a fixed speculation setting.

Instead, it sizes the speculative tree from measured draft and verification costs for the batch size, hardware and workload it is actually running on, while preserving the target model's output distribution.

The EAGLE-4 draft combines three components: a sliding-window draft layer, a low-rank candidate head and an append-only draft cache. Dense and latent-MoE draft structures are both implemented. The measured target pair is Qwen3.8-27B with its EAGLE-4 draft.

The eagle-harness package, installable from PyPI, serves these drafts on SGLang, vLLM and TokenSpeed. It attaches through hooks the engine already exposes rather than patching the engine at runtime. Stock engine packages do not carry those hooks, so builders must install pinned, patched engine wheels or container images. The release settings file holds every version pin and index URL, and the v0.1.0 release attaches the wheels directly.

Benchmark results are reported per engine against a matched no-speculation control, with conditions stated for each row. No TokenSpeed throughput is claimed.

The catch: This is a first public release, v0.1.0, with the throughput claims resting on a single model pair and a specific GPU configuration (4× NVIDIA B300). The engine dependency means adoption requires maintaining patched builds of SGLang, vLLM or TokenSpeed, which will track upstream only as quickly as the pins are updated.

Use Cases
  • Inference engineers serving Qwen3.8-27B who want faster generation without output changes.
  • Platform teams running SGLang, vLLM or TokenSpeed clusters seeking adaptive speculative decoding.
  • Researchers benchmarking dense versus latent-MoE draft structures for speculative decoding.

Agent-Driven E2E Framework Replays Recorded Tests Without Model Calls 🔗

New `@e2e-dev/testmu` package runs mobile targets on TestMu AI emulators, simulators, and real devices

tester-army/e2e · TypeScript · 11.6k stars 3mo old

The e2e framework lets teams describe a test goal in plain language, then has an agent drive a web or mobile app to reach it. Assertions and locators sit alongside those steps in the same test.

The efficiency trick is recording. Once an agent step is verified by a later assertion, its actions are saved. Subsequent runs replay them with no model calls until the app changes. Tests with no agent steps need no model at all.

The newest change is the @e2e-dev/testmu package. It routes a mobile target to TestMu AI (formerly LambdaTest) Android emulators, iOS simulators, or real devices, one per worker slot. Each attempt can link to a video of its session.

Setup is handled by npx e2e init, which picks an engine and a model provider. Nine example projects, from Vite to Flutter, ship as standalone suites.

The catch: the project is pre-1.0, so APIs and config can change between minor releases, and it has 97 open issues.

Use Cases
  • Mobile QA engineers running Android and iOS suites on TestMu AI devices
  • Web teams replacing brittle selectors with natural-language test goals
  • CI maintainers cutting model costs by replaying verified agent runs
