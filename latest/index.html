Native Zig Server Lets Mac Owners Run Any LLM Locally, Without Python 🔗

One binary on Apple Silicon serves OpenAI and Anthropic APIs, plus image, video, music and speech generation.

ddalcu/mlx-serve · Zig · ▲ 19 in 1d 8mo old · Latest: v26.10.2

mlx-serve runs large language models on Apple Silicon with no Python runtime, no cloud dependency and no Electron shell. Written in Zig, it loads both MLX-format models and any GGUF model on HuggingFace, then exposes OpenAI-compatible and Anthropic-compatible HTTP endpoints on localhost:11234.

That means tools built for those APIs, including Claude Code, the OpenAI SDK, Cursor and Open WebUI, can point at a local Mac without code changes.

The latest release extends the server beyond text. The same process now handles:

  • Video: storyboards that chain shots into clips of up to two minutes.
  • Music: full songs with vocals from lyrics, plus a streaming "AI Radio" mode.
  • Sound effects and speech, including voice cloning.
  • Images: Qwen-Image-2.1-Turbo renders 1024x1024 images in about 8 seconds on an M5 Ultra, per the project's own figures.

Chat and agent sessions keep responding while generation jobs run on the same server. A signed, notarized menu-bar app, MLX-Serve.app, wraps the binary with a model browser, chat window, MCP tool calling and a settings panel, so no terminal is required. Linux CUDA builds are also published for NVIDIA hardware.

The project's README claims it is faster than LM Studio on identical MLX weights. Those benchmarks are self-reported and have not been independently verified.

The catch: The project is about eight months old, with 48 open issues and a single-maintainer footprint visible from the repository. Its scope is wide: text, image, video, audio and 3D on one server. Builders should test stability and throughput on their own workloads before routing production traffic through it, and should note that the app requires macOS 26.2 or later.

Why this leads today It leads because mlx-serve offers something newly possible rather than a familiar pattern: a Python-free, Zig-backed inference server for Apple Silicon that speaks both OpenAI and Anthropic APIs, while the rival candidates are mature, well-trodden categories.

Use Cases
  • Mac developers routing Claude Code sessions to a private local model.
  • Indie teams prototyping agents offline without paying per-token cloud fees.
  • Creators generating storyboards, songs and sound effects on a Mac Studio.

Overdrive Revives Dead PS5 Homebrew Store, Source Now Fully Open 🔗

Rebuilt from a decompiled binary, the store installs 1,800-plus games directly onto jailbroken consoles with no PC needed.

MyLuxy/overdrive · C++ · 552 stars 3d old

The original Overdrive project has been shut down. A developer working under the handle MyLuxy decompiled the last released build, recovered the complete C++ source and rebuilt it in the open, restoring a homebrew game store for jailbroken PS5 consoles.

The store catalogs more than 1,800 games with filters, sorting, scores and download sizes. Downloads go straight to the console, internal storage or any USB drive, with live speed and storage stats. Version 1.0.5 adds a self-updater that installs new versions from the console itself.

The install path is deliberately minimal. Users place a single Overdrive.exfat image inside a homebrew folder on an exFAT USB drive. ShadowMount+ detects the file, mounts it and installs it without user input. The release also fixes several download-host failures and extraction errors, and adds a home page that changes each launch.

  • Target: jailbroken PS5 owners running ShadowMount+ and kstuff
  • Interest: reverse engineers studying decompilation recovery
  • Interest: homebrew developers building console storefronts

The catch: The project depends on two third-party payloads and a jailbroken console, and its legal footing rests on a shut-down predecessor. The repository has 16 open issues, and its library links to third-party download hosts whose reliability and legitimacy the project does not control.

AnyPS5 Tool Ports PS5 Executables to Linux and Windows 🔗

Relinker converts binaries natively, with no emulator or runtime process.

boykopovar/AnyPS5 · C++ · 40.4k stars 2mo old

AnyPS5 is a C++ tool that automatically converts PS5 executables into formats native to Linux and Windows. A web converter handles the work in the browser, and files stay on the user's machine.

The project includes a relinker that rewrites executables for the target system and reimplements PS5 system PRX libraries for dynamic linking. Instead of emulating the console, it runs ported code directly.

The shader recompiler produces SPIR-V, validated through Spirv-Tools when built with ANYPS5_ENABLE_SPIRV_TOOLS. SDL-mapped controllers, including analog sticks and triggers, are supported, and keyboard and mouse can be configured through anyps5-input.ini.

Library coverage is measured only against functions the project has declared, not the full PS5 API. The project is licensed GPLv2 and says it ships no copyrighted firmware or keys.

The catch: Coverage is partial and self-measured, with 933 open issues and the latest release at v0.1.2, so a builder should check the per-game blocker map before assuming a title will run.

  • Vulkan developers researching PS5 shader translation into SPIR-V pipelines
  • Interoperability researchers examining PS5 system library behavior for compatibility work

Earshot Gives Coding Agents Ears to Hear the Sound They Write 🔗

CPU-only open-source toolkit turns AI-made audio into evidence agents can measure, revise, and reproduce from code

Leonxlnx/earshot · Python · 491 stars 2d old

AI coding agents can now write the code that renders a film or game, but they cannot hear what they produced. earshot closes that gap.

It turns sound into text an agent can reason about: what a file sounds like, how well it matches a description, and where a hit lands against the cut.

The project works in three directions:

  • Listening: a second-by-second transcript and annotated spectrogram of a full film, scored against professional launch films.
  • Forging: agents write sounds as physical-synthesis recipes, and a critic built on earshot scores each candidate. Forge v2 covers 34 sound types, from whooshes to UI clicks.
  • Fitting: earshot fit converts a recording into a readable Python recipe. On 12 real recordings, the code renders reached a median 0.945 CLAP similarity.

It runs locally as a CLI, a Python API, or an MCP server.

The catch: Each CLI call reloads models for 20 to 40 seconds, the project is at v0.2.0 with two open issues, and builders will need to judge whether code-synthesized sound suits their production.

Use Cases
  • Game developers generating and auditing UI sound effects inside automated build pipelines
  • Motion designers having agents iterate on whooshes and stings from code
  • Audio engineers converting recordings into editable, parametric Python recipes

Open-Source gitai Brings Agent-Scale Version Control to Builders 🔗

MIT-licensed server lands code with compare-and-swap instead of merge queues, works with any model provider

feder-cr/git-ai · Go · 1.1k stars 1d old

Coding agents make thousands of short-lived commits that touch a few files each, colliding on the same branches. Classic Git hosting, built for humans who clone and push once, becomes the bottleneck.

gitai moves the work to the server. Clients stay online and fetch only what they need. History queries are answered and cached server-side. Changes land through a compare-and-swap rather than a queue, and every update is recorded in a changeset log.

The project is an independent, MIT-licensed implementation of a design Anthropic described publicly but does not release. It is a fork of GitLab's Gitaly, and repositories remain normal Git repositories underneath. The server never calls a language model, so AI features work with any provider or none.

Version 0.1.0 is the first public release, and the repository has no open issues. Builds require Go 1.26, a C toolchain, and Meson.

The catch: the project is a day-old v0.1.0 with 117 forks and no track record, so teams should test it before trusting it with production branches.

Use Cases
  • Platform teams running hundreds of coding agents against shared branches
  • Self-hosters seeking agent-scale Git without vendor lock-in
  • Open-source maintainers accepting high-volume automated pull requests
